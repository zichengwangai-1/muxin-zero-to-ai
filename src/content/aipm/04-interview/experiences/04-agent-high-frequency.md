# Agent 高频面试题：从真假需求到上线评测

**来源性质**：根据已收集的 Agent 搭建、办公智能体、客服 Agent、工具调用与评测面经整理。参考答案是对多份原始观点的合并，不代表某位作者的逐字回答。

## 面经里问了什么

- 如何从零设计一个旅行规划 Agent？
- 如何判断一个需求真的需要 Agent，而不是普通工作流？
- Agent 和传统 Chatbot 的本质区别是什么？
- Agent 的核心架构和主流开发框架有哪些？
- 如何设计以会议、邮件为主的办公 Agent？
- Agent 的工具调用模板怎么写？
- 面对模糊需求，Agent 如何澄清并个性化执行？
- 如何评估 Agent 是否靠谱？

## 考察点

- 是否先定义自主性边界，而不是直接列功能。
- 是否理解规划、工具、记忆、状态、权限和反馈组成完整系统。
- 是否关注异常、重试、循环、越权与人工接管。
- 是否同时评估最终结果和执行过程。

## 小白怎么理解

普通聊天机器人主要“给答案”，Agent 还会“替你做事”。只要系统能调用日历、发邮件、改订单或操作资金，风险就从答错一句话升级为做错一件事，所以必须把确认、权限、审计和撤销设计进去。

不是所有自动化都需要 Agent。规则稳定、步骤固定、失败代价高的流程，传统工作流往往更便宜、更稳定。只有任务需要理解模糊目标、动态选择步骤或调用多个工具时，Agent 才更有价值。

## 参考答案

### 先判断是不是真 Agent 需求

依次看四点：任务是否高频且有价值、步骤是否会随环境变化、是否需要跨工具决策、是否有可验证的结果和反馈。若只是固定表单流转，不必强行使用 Agent。

### 再搭六层能力

1. **目标与边界**：全自主还是关键步骤确认，哪些事禁止做。
2. **规划与路由**：如何拆任务，何时走规则、检索或工具。
3. **工具**：每个工具的输入、输出、权限、超时和失败处理。
4. **记忆**：当前任务状态、长期偏好分别存什么，何时读取和更新。
5. **执行状态**：向用户说明做到哪一步，避免长时间无反馈。
6. **验证与兜底**：关键结果校验、失败重试、停止条件和人工接管。

### 如何评估 Agent

原始面经用“诚、快、省、稳、安全”概括，其中“诚”实际指任务是否完成。为避免小白误解，这里记成 **成、快、省、稳、安**：

| 指标 | 要看什么 |
|---|---|
| 成 | 任务是否真正完成，结果是否写入目标系统 |
| 快 | 完成时长、对话轮次、工具调用次数、是否循环 |
| 省 | Token、API、人工兜底和单任务总成本 |
| 稳 | 同一任务多次运行是否稳定，复杂输入是否崩溃 |
| 安 | 是否越权、误操作、泄露数据或给出违规建议 |

评测任务来自真实用户、历史失败、竞品典型任务和人工构造的边界场景。还应与旧流程、简化版 Agent 做对照，证明复杂方案是否真的更好。

## 追问延伸

- Agent 卡在循环里怎么办？设置最大步数、重复动作检测、超时、状态检查与降级路线。
- 长任务是不是失败？不是。要区分总耗时与感知等待，通过进度、阶段结果和可恢复执行管理体验。
- Memory 如何防止污染？按来源和可信度分级，设置过期、冲突和用户删除机制。

## 一句话记忆

**Agent 会替用户做事，所以先划边界，再管规划、工具、记忆、状态和兜底。**
