# Model or Harness：Agent 出错后，先修模型还是修系统？

## 一句话说清

同一个失败表象，可能来自模型、工具、记忆、运行框架、用户输入或评测环境；先找到责任位置，再决定修什么。

## 论文要解决什么问题

Agent 失败后，团队经常直接得出“模型不够强”的结论。但模型可能已经做对判断，只是工具返回错误；也可能是系统没有保存关键记忆，或评测器把正确结果判错。

如果不能定位故障来源，团队就会花钱换模型，却没有修到真正的问题。

## 它是怎么做的

论文把 Agent 系统拆成模型、运行框架、用户、工具、记忆和环境等组件，并把 41 种失败模式放到组件之间的交互边上，再标明应该由哪一侧负责修复。

作者使用公开基准、系统卡、研究报告和 Agent 轨迹构建案例，并测试模型能否复现这套分类。

## 关键发现

在四个前沿模型中，表现最好的自动分类器与人工标签达到 Cohen's κ=0.76。它说明这套故障语言具有一定可复现性，但仍不等于可以完全替代人工诊断。

## 小白怎么理解

外卖迟到，不一定是骑手慢，也可能是商家出餐晚、地址写错或平台路线错误。Agent 也是一样，看到“任务失败”不能立刻把锅甩给模型。

## 对 AI 产品经理的五层启发

### 1. 用户价值：错误提示要告诉用户下一步怎么办

不同故障需要不同恢复方式。工具没权限应引导授权，需求不清应追问，模型不确定应提示核验。统一显示“生成失败，请重试”会让用户反复撞墙。

### 2. 产品机制：把系统链路变成可观察的状态

Agent 应记录计划、模型调用、工具输入输出、记忆读取和最终验收。产品界面不必暴露全部日志，但后台必须能回答“在哪一步、因为什么、由谁恢复”。

### 3. 指标体系：按责任归因统计失败

除了总成功率，还要看模型判断错误率、工具失败率、权限阻断率、记忆缺失率、环境异常率和评测误判率。只有这样才能知道下一笔资源应该投入哪里。

### 4. 风险边界：自动归因也可能归错

多个问题可能同时出现，例如工具返回脏数据导致模型推理错误。高风险故障需要保留原始证据和人工复盘，不能让自动分类结果直接触发大规模模型更换。

### 5. 产品决策：先修高频且可控的链路问题

如果 40% 的失败来自权限和工具超时，优先修接口比升级模型更划算。产品经理应把“影响用户数 × 修复收益 × 开发成本”作为排序依据。

## 如果落到真实产品

在企业知识库 Agent 中，我会把 Bad Case 标成检索不到、检索错误、模型未引用、权限不足、答案过期和评测误判。每周按业务损失排序，分别交给检索、模型、数据或平台团队，而不是建立一个没人负责的“回答不好”大类。

## 面试参考答案

我最近读了 Model or Harness。论文提出 41 类 Agent 故障，并把问题定位到模型、框架、工具、记忆、用户与环境之间的具体交互。它对产品经理最大的启发是，Bad Case 分类必须直接指向可执行的修复责任。

我不会看到效果差就先换模型，而会先建立端到端日志和故障树，统计每类问题的频率、损失与可修复性。这样可以判断应该优化 Prompt、修工具、补数据、调整权限，还是确实需要换模型。

## 追问准备

### 一个问题同时涉及多个组件怎么办？

区分根因和连锁结果。例如检索返回错误文档是根因，模型基于错误文档生成错误答案是结果；复盘时保留两者，但修复优先指向根因。

### 如何验证分类真的有用？

看同类问题是否被同一种改动稳定降低，以及每个类别能否明确分配负责人和验收指标。
