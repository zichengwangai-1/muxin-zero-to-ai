# Agentic Workloads：Agent 慢和贵，问题可能不在大模型

## 一句话说清

Agent 是模型、检索、工具、沙箱和长期状态组成的系统；只优化模型推理，可能忽略一半以上的真实瓶颈。

## 论文要解决什么问题

传统服务系统针对单次模型推理优化，但 Agent 会持续调用工具、保存状态、运行代码并多轮交互。团队如果只看模型时延和显存，就无法解释任务为什么仍然慢、贵或不稳定。

## 它是怎么做的

论文构建 AgentSysBench，对十种代表性 Agent 应用进行统一的系统级观测，并结合生产轨迹分析模型、检索、沙箱、工具调用、状态保存和上下文开销。

## 关键发现

- 10 个应用中有 5 个主要时延来自非 LLM 组件；
- GPU 推理、内存型检索和 CPU 沙箱的任务时延最多相差 32 倍；
- 单会话沙箱工作集内存峰值可达 28GB；
- 任务感知服务降低 29%–40% 时延；
- 状态卸载降低 4.6 倍内存使用；
- 工具结果缓存消除 35.2% 的重复搜索调用，并节省 19.3% 的总体搜索时延。

这些是论文所测系统的结果，具体产品需要重新测量自己的链路。

## 小白怎么理解

餐厅出餐慢，不一定是厨师炒菜慢，也可能是找食材、等餐具、传菜和结账慢。Agent 的模型只是“厨师”，整条服务链都可能成为瓶颈。

## 对 AI 产品经理的五层启发

### 1. 用户价值：用户感知的是端到端完成时间

用户不关心模型首字多快，而关心任务什么时候真的完成。产品要展示阶段状态和可用中间结果，避免用户在工具或沙箱等待期间只看到空转。

### 2. 产品机制：按任务阶段使用不同资源

模型推理、搜索、文件处理和代码执行的资源需求不同。系统可以并行无依赖步骤、缓存重复工具结果、闲置时卸载状态，并为长任务支持断点恢复。

### 3. 指标体系：拆开每一段时延和成本

- 端到端任务完成时间；
- 模型、检索、工具、沙箱各自占比；
- 有效工作时间与等待时间；
- 重复工具调用率、缓存命中率；
- 每个成功任务的总成本。

### 4. 风险边界：缓存和卸载不能牺牲新鲜度与状态一致性

搜索结果可能过期，跨用户缓存可能泄露数据，状态恢复也可能漏掉权限变化。产品需要缓存时效、用户隔离和恢复校验。

### 5. 产品决策：优化前先做端到端观测

不要因为模型账单显眼就先换便宜模型。先找出时间和成本真正花在哪里，再比较缓存、并行、路由、状态卸载或模型替换的收益。

## 如果落到真实产品

在 AI 深度研究产品中，我会把耗时拆为规划、搜索、抓取、阅读、写作和引用核验。如果搜索重复率高，先做结果缓存；如果网页抓取占主要时间，优化并发与失败重试；只有模型生成本身是瓶颈时才更换模型。

## 面试参考答案

我最近读了 Agentic Workloads 的系统分析。论文在十种应用中发现，一半的主要时延来自非模型组件，还展示了缓存、任务感知调度和状态卸载能够明显改善时延与资源使用。

它对产品经理的启发是，Agent 的成本和体验必须端到端管理。我会先埋点拆出模型、检索、工具和沙箱占比，再按瓶颈选择方案，同时监控缓存新鲜度、状态恢复和每个成功任务的总成本。

## 追问准备

### 为什么首 Token 时延不够？

Agent 在输出前后还会调用工具、等待环境和多轮验证，首 Token 只覆盖一次模型响应的开头，不能代表任务完成。

### 缓存最适合什么内容？

高重复、短时间内稳定、权限边界清楚的工具结果；实时价格、用户私有数据和高风险决策需要更严格的失效策略。

**Agent 慢别只催模型，先看整条流水线堵在哪里。**
