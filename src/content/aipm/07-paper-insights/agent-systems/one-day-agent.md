# OneDayAgent：怎样让 Agent 完成持续一天的复杂任务？

## 一句话说清

OneDayAgent 把开放式长任务变成可管理的执行过程：拆成有边界的小任务，在上下文压力下保留执行记忆，并在最后验证和修复交付物。

## 论文要解决什么问题

真实任务可能跨越工作、学习和生活，包含网页、文档、图片和多个工具。任务一长，Agent 容易忘记最初目标、丢失中间状态、上下文溢出，或者产出很多文件却没有真正完成交付。

## 它是怎么做的

OneDayAgent 提供一套长任务 Harness：先拆解任务，管理子任务边界与执行记忆，再检查最终交付物并进行修复。它强调的是模型外部的执行结构，而不是换一个更大的模型。

## 关键发现

论文在包含 104 个任务的 AgentIF-OneDay 上评测。使用 GLM-5.2 时，总体得分为 0.821；同一套 Harness 也运行在来自三个模型家族的五个后端模型上。作者据此认为它能在不针对单一模型调参的情况下跨后端工作。论文同时标注为 ongoing work，结论仍需后续复现。

## 小白怎么理解

让一个人说“帮我办完一场活动”很容易失控。更可靠的方式是先列清单，每一步都留下进度和材料，最后按验收表检查，而不是只问一句“做完了吗”。

## 对 AI 产品经理的五层启发

### 1. 用户价值：用户要的是交付物，不是长时间运行

产品不应把“运行了多少步”当成能力。用户需要的是文件完整、链接可用、约束满足，并且中途能看到进展和接管。

### 2. 产品机制：任务必须有边界、状态和验收

每个子任务要写清输入、预期输出、依赖和完成条件；阶段结果进入执行记忆；最终验收应该回到用户最初的目标，而不是只汇总 Agent 自己做过什么。

### 3. 指标体系：评测整条任务链

除最终成功率外，还要看子任务完成率、返工次数、目标漂移率、用户接管点、工具失败恢复率，以及交付物通过验收的比例。

### 4. 风险边界：越长的任务越需要可暂停和可追溯

长任务会持续消耗资源并积累错误。用户应该能看到计划、暂停执行、修改约束和回到稳定检查点。高风险动作必须单独确认。

### 5. 产品决策：优先投资 Harness，而不是盲目追最新模型

如果失败来自目标漂移、工具错误和缺少验收，只换更强模型不一定解决。产品团队应把模型、工具、记忆、任务状态和验证器作为一个系统共同评测。

## 如果落到真实产品

以“帮我完成一份竞品调研”为例，我会要求系统：

1. 先确认研究范围和交付格式；
2. 把检索、筛选、验证、比较和写作拆成独立阶段；
3. 每阶段保存来源和结论，避免上下文压缩后丢失；
4. 最后按覆盖范围、引用有效性和结论一致性验收；
5. 未通过的部分只局部返工，而不是整份重做。

## 面试参考答案

OneDayAgent 让我意识到，长任务 Agent 的核心竞争力不只是模型，而是 Harness。它通过任务拆解、执行记忆和最终验证，把开放式请求变成可管理流程，并在 104 个任务上展示了跨多个模型后端工作的能力。

如果我设计这类产品，会让每个子任务都有输入、输出和完成条件，并向用户展示计划、进度和接管点。评测除了最终成功率，还看目标漂移、工具失败恢复、返工次数和交付物验收率。只有这样，Agent 才是可管理的执行者，而不是一个运行很久的聊天框。

## 追问准备

### Harness 是什么？

可以把它理解为模型外面的工作系统，负责给模型提供工具、记忆、任务状态、执行规则和结果检查。

### 为什么更强模型还需要 Harness？

模型能力解决单步理解和生成，但长任务还会遇到状态丢失、工具失败、权限和验收问题，这些需要系统机制配合。

## 一句话记忆

**长任务不是让模型一直跑，而是拆得开、记得住、验得过。**
