# Context as an Environment：超长任务不该把所有历史都塞进 Prompt

## 一句话说清

Scroll 把完整历史保存在可追溯的事件日志中，让 Agent 用代码按需取出当前需要的信息，而不是每轮都把全部记忆塞回上下文。

## 论文要解决什么问题

长任务会快速超过模型的上下文窗口。常见做法是压缩旧对话或提前提取记忆，但当时并不知道未来需要什么，一旦删错，后面很难恢复。

## 它是怎么做的

Scroll 把每个会话看成可执行环境：

- 用只追加的 Event Log 保存完整历史；
- 用持久化 Python 环境保存工具结果、变量和派生状态；
- 由模型编写代码检索和整理状态；
- 只有明确输出的内容才进入下一轮工作上下文；
- 被移出的内容仍保留地址，可以再次找回。

## 关键发现

论文使用 Qwen3.8-Max 测试，报告在 LongMemEval_S 达到 94.8%，在 BEAM_10M 达到 73.1%，在 LOCA_256K 达到 86.7%。这是论文基准结果，不代表所有业务数据和模型都能达到同样表现。

## 小白怎么理解

不是把整个仓库搬到办公桌上，而是保留一套完整档案和索引；当前只拿出正在处理的几份文件，需要时还能按地址找回旧材料。

## 对 AI 产品经理的五层启发

### 1. 用户价值：长任务要“记得住，也找得回”

用户真正需要的不是 Agent 记住每一句话，而是在关键时刻找回目标、约束、决策和证据。产品应让用户看到当前引用了哪些历史，并能纠正错误记忆。

### 2. 产品机制：分离永久记录与当前工作区

永久层保存原始事件，工作层只放当前任务必要信息。摘要可以提高效率，但不能成为唯一真相；任何重要结论都要能回到原始记录。

### 3. 指标体系：不只测“能否找到”

- 关键约束召回率；
- 检索到错误或无关历史的比例；
- 恢复旧信息所需时间；
- 上下文 Token、延迟与任务成功率；
- 用户纠正记忆后的生效率。

### 4. 风险边界：完整日志带来隐私和权限问题

保留越多，泄露风险越大。产品需要数据分级、过期删除、可见权限和审计记录；检索时也要继承原数据权限，不能因为进入记忆库就越权。

### 5. 产品决策：先找“必须原样保存”的信息

合同条款、安全规则和用户明确约束适合保留原文；普通闲聊可以摘要；临时工具输出可以按需清理。不同信息采用不同保留策略，比统一压缩更可靠。

## 如果落到真实产品

在长期项目助理中，我会把原始会议记录、明确决策和任务状态分别存储。首页只展示当前目标、下一步和风险；点击任何结论都能回到原始会议段落。用户删除某条记录后，相关记忆索引也必须同步失效。

## 面试参考答案

我最近读了 Context as an Environment。它没有继续扩大 Prompt，而是把完整历史放在事件日志和持久化环境里，让 Agent 用代码按需构造当前上下文。对产品经理的启发是，记忆产品要分开“保存”和“使用”：完整记录负责可追溯，工作区负责效率。

落地时我会按信息类型设计保留策略，并同时测关键约束召回率、无关信息干扰、成本和用户纠错。还要把权限和删除能力做进记忆层，否则记得越多，隐私风险也越大。

## 追问准备

### 与普通 RAG 有什么区别？

RAG 常从外部文档库检索片段；这里还管理会话事件、变量、工具结果和不断变化的任务状态，并强调可执行的状态处理。

### 为什么不直接使用超长上下文模型？

更长窗口仍有成本、注意力稀释和隐私问题，而且长任务最终仍可能超过窗口；结构化管理与长上下文可以同时使用。

## 一句话记忆

**长任务不是全塞进脑子，而是建档案、做索引、用时再取。**
